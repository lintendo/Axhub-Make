# PLAN 原型

## 目标与边界

主流程保持不变：

```text
读取上下文 -> 产品需求对齐 -> DESIGN.md 候选与设计方向对齐 -> 创建/更新主规格草案 -> 围绕主规格多轮评审与确认 -> 实现 -> 同步主规格 -> 提供预览链接 -> 验收
```

本技能是完成“读取上下文 -> 产品需求对齐 -> DESIGN.md 候选与设计方向对齐”后进入的规划分支。未完成前置流程时不得进入规划分支；不在本技能中重复前置流程，也不跳过前置流程直接规划页面。

这个技能只负责“规划并初始化”。它把整体拆分和每个原型的初始主规格对齐清楚，然后一次性创建每个原型的 HTML 主规格和可运行占位骨架。技能完成后立即结束，把具体页面生成交回现有原型开发规范。

不生成完整页面、真实素材、业务数据或复杂交互，不创建页面级规格文档或额外计划文档。不创建 `PLAN.md`、`PROJECT.md`。不创建跨原型总规格或页面级独立规格文件。

## 工作流程

### 1. 在对话中对齐初步方案

沿用前置流程已经读取并确认的上下文；只补充会影响原型拆分、页面关系或骨架初始化的必要事实，不重新开启产品需求或设计候选流程。

先在对话中对齐初步方案，不创建文件。至少收敛这些会改变拆分结果的内容：

- 原型数量、每个原型的职责和建议 id。
- 每个原型包含哪些内部页面，以及默认入口页。
- 原型之间的关系、跳转边界和共享内容。
- 公共设计基底或每个原型的设计方向。
- 大致执行顺序和页面批次；批次只做初步建议，不在这里生成页面。

需要时一次只问一个关键问题，并给出推荐答案。用户明确确认原型拆分后，才进入下一步。

### 2. 分别确认每个原型的初始主规格

用户确认原型拆分后，逐个确认每个原型的初始主规格。这里确认的是核心设计和页面情况，不是每个页面的完整需求，也不替代后续的需求对齐与规格确认流程。

每个原型至少确认：

- 原型目标、核心用户/场景和整体体验。
- 页面列表、每个页面的作用和简短占位描述。
- 页面之间的关系、入口、默认页和主要路径。
- 页面批次的初步分组与执行顺序。
- 记录前置流程已确认的 `DESIGN.md`、设计方向和明确的特有调整；除非出现会改变范围的冲突，否则不重新选择设计候选。
- 当前范围、不做内容、必要假设和仍需后续确认的问题。

确认结果只写入该原型自己的 `.spec/spec.html`，不要为了初始规划另建文档。每个原型独立维护自己的规格文档。所有原型的初始主规格都确认后，才一次性创建骨架。

### 3. 一次性创建规格与原型骨架

这里要一次性创建全部原型的 HTML 主规格骨架，同时创建全部原型骨架；不能只写计划或只创建规格文件。

为每个确认的原型创建以下结构：

```text
src/prototypes/<prototype-id>/
├── index.tsx
└── .spec/
    └── spec.html
```

主规格固定落在 `src/prototypes/<prototype-id>/.spec/spec.html`，原型入口固定落在 `src/prototypes/<prototype-id>/index.tsx`。

固定使用 `.spec/spec.html` 作为主规格，不询问 Markdown/HTML。以 `templates/prototype-spec.html` 为起点，改写为当前原型的单文件规格：

- 保留一个原型总览入口。
- 为页面列表创建可点击的内部规格入口；页面规格仍在同一个 `spec.html` 内，不拆文件。
- 在页面标题和目录项中写入 `[待完善]`；页面规格完成并进入生成时改为 `[生成中]`，完成后移除标记。没有状态标记即表示已完成，不写“已完成”。
- 页面目录必须包含页面 id、名称、作用、批次和简短描述；初始描述可以是“页面规划中，待补充详细规格”。
- 记录核心设计方向、原型范围、页面关系、初步执行批次和当前假设。

同时创建可运行的 `index.tsx` 原型骨架：

- 顶部包含面向用户的 `@name`。
- 使用 `defineHashPageRoute` / `useHashPage`（或项目已有等价路由模式）注册全部页面，页面 id 只使用小写字母、数字和连字符。
- 每个页面都能通过 `#page=<page-id>` 访问；默认页与规格目录一致。
- 每个页面只显示稳定、简单的占位提示（简单占位提示），例如页面名称、作用和“页面规划中”；不要添加正式视觉设计、真实素材、业务逻辑或复杂交互。
- 原型目录、入口、页面路由和规格文件必须一次性完整创建，不只创建规格文档。

创建后做最小结构检查，确认每个原型都有 `index.tsx`、`.spec/spec.html`、默认页和全部页面路由；按项目现有方式可运行检查时，再使用 `node scripts/check-app-ready.mjs /prototypes/<prototype-id>` 排除启动或路由错误。

## 状态约定

只允许使用两种显式标记：

- `[待完善]`：页面仍是计划占位，详细规格或实现尚未完成。
- `[生成中]`：后续某个执行批次已经开始生成该页面。

没有状态标记就是完成状态。不要引入“待确认”“待验收”“已完成”等额外状态，也不要在规格里维护第二套状态表；目录标题就是状态面板。

## 技能结束时的交互交接

创建并检查全部骨架后，技能到此结束，不要在当前技能中继续生成页面。最终回复必须说明：

- 创建完成的原型列表、目录路径和主规格路径。
- 每个原型的页面列表、页面 id、初始批次和当前状态。
- 仍需补充的初始假设或页面规格缺口。
- 后续建议：建议用户为每个原型或批次新开一个对话，也可以建议使用子代理分别完成页面任务。

交接时明确提醒后续对话或子代理：先读取目标原型的 `.spec/spec.html`、`rules/requirements-alignment-guide.md` 和 `rules/prototype-development-guide.md`，再按现有的需求对齐、主规格确认、原型实现、规格同步和验收流程继续；不要重新运行本技能，也不要跳过页面级规格确认直接生成完整页面。
