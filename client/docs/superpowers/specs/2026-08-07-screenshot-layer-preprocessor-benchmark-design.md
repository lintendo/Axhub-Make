# 截图图层预处理器单图验证设计

## 背景

当前 `screenshot-to-prototype` 已规定“HTML 主规格确认后才能进入 React”，但第一版 HTML 主规格仍主要由 Agent 手工完成元素清单、bbox、候选素材、规格 HTML、资源路由和截图校验。近期三次实际任务显示，首轮 HTML 规格约需 38–41 分钟，后续两条视觉批注也约需 14 分钟。主要耗时不在单次模型推理，而在重复的人工式结构整理、HTML 编写、素材路由和验证修复。

历史实验已经证明，本机视觉模型可以在约 10 秒量级完成开放物体识别与 SAM 分割，但 Florence-2、YOLO 等语义模型不应继续成为默认依赖：当前对话 AI 可以在后续阶段承担命名、分组和表示方式判断，本地只保留必须可重复执行的 OCR、几何分析、蒙版和图像导出能力。

本设计先验证“图层优先”的机器底稿，不直接改造正式技能。验证图固定为 `src/resources/image-2.png` 的 `863×1823` 政务服务首页。

## 目标

1. 用本地脚本把源图拆成互斥图层并生成可交互的机器 HTML。
2. 同时输出 OCR、图层清单、运行指标和综合评审页，让用户能判断图层是否有后续语义化价值。
3. 机器 HTML 一生成并通过基础加载检查，立即交付用户确认并停止。
4. 只有用户明确指令“进入 AI 评审”后，才允许生成 AI patch 和第二版混合可编辑 HTML。
5. 保持现有核心流程不变：最终仍需 HTML 主规格确认，确认后才能进入 React。

本轮不预设 5、10 或 15 分钟 SLA。先记录冷启动与热运行的真实耗时，用户看过效果后再决定正式目标。

## 非目标

- 不修改 `.agents/skills/screenshot-to-prototype/` 或其正式测试。
- 不创建或修改任何 React 原型文件。
- 不把机器图层 HTML 视为最终主规格。
- 不在第一阶段自动执行 AI 语义评审、AI 视觉修正或图片生成。
- 不为被遮挡物体补全不可见区域，也不承诺图层移动后背景已经完成生成式修补。
- 不提交 `.local/` 下的脚本、模型缓存、截图或生成报告。

## 已确认决策

- 首轮路线采用“图层优先”，而不是直接生成完整语义 DOM。
- 默认依赖当前对话 AI 完成第二阶段语义分组，不打包本地 Florence-2 作为默认语义回退。
- OCR 使用专用 OCR 引擎获取文字、四边形和置信度；通用 AI 不作为像素坐标事实源。
- 第一阶段只评审图层与 OCR 的可用性；第二阶段才评审可编辑 HTML 的视觉和结构质量。
- 测试设置两个明确停点：机器 HTML 停一次，AI 评审 HTML 再停一次。
- 用户拒绝额外的可视化样例选择页，测试直接使用政务服务截图。

## 模型与工具边界

### 第一阶段默认能力

- RapidOCR 作为跨平台 OCR 运行时。
- PP-OCRv6 small 作为本次普通设备基准模型，输出文字、四边形和置信度。
- SAM 2.1 Tiny 负责候选蒙版。
- 连通域、颜色区域、面积、IoU 和包含关系用于候选过滤与互斥像素分配。
- 浏览器只做机器 HTML 的加载、尺寸、资源和交互冒烟检查。

### 本轮不加载的能力

- Florence-2：语义理解留给第二阶段对话 AI。
- YOLO：固定类别不适合作为通用 UI 截图默认检测器。
- PaddleOCR-VL 或 PP-Structure：本轮是 UI 截图文字定位，不是复杂文档解析。
- `rembg` 和图片生成：只在后续 AI 评审明确标记复杂透明素材时按需进入，不参与第一阶段机器底稿。

正式接入时可以增加 PP-OCRv6 medium 的低置信度区域回退，但本次单图验证固定使用 small，避免一次实验混入两个模型变量。

## 总体架构

```text
源图
  ↓
源图摘要与缓存键
  ↓
RapidOCR：文字、四边形、置信度、阅读顺序
  ↓
SAM 2 + 传统图像规则：候选蒙版与区域
  ↓
候选去重、嵌套整理、互斥像素归属
  ↓
base layer + 精确源像素图层 + OCR 草稿
  ↓
machine.html + review.html + 指标
  ↓
基础加载验证
  ↓
【停点一：交付用户确认】
  ↓ 用户明确要求进入 AI 评审
AI 读取源图、OCR、图层和评审结果，输出 ai-patch.json
  ↓
脚本应用 patch，生成 ai-reviewed.html
  ↓
【停点二：交付用户确认】
  ↓ 后续另行确认
正式技能集成与现有 HTML 主规格流程
```

## 组件边界

### 1. 源图准备器

读取尺寸、色彩、alpha、SHA-256 和 viewport，生成稳定缓存键。所有后续产物记录源图 hash、模型版本和参数，避免旧结果误用于新截图。

### 2. OCR 适配器

只负责返回原始识别事实，不推断 DOM：

- 四点坐标。
- 识别文字。
- 置信度。
- 初步阅读顺序。
- 使用的模型和运行时版本。

OCR 结果必须保留原始输出，后续 AI 修正另写 patch，不覆盖原始事实。

### 3. 图层候选器

SAM 2.1 Tiny 生成候选蒙版；传统规则补充颜色连续区域和连通域。候选器不命名业务语义，只记录稳定 ID、bbox、面积、分割分数和来源。

候选按 IoU、包含率和面积过滤：重复候选只保留质量更高者；过小、低置信度或严重碎片化的候选标记为 `unresolved`，其像素继续留在 base layer。

### 4. 像素归属器

第一阶段的目标是可检查的无损分层：

- OCR 矩形层优先于普通视觉候选。
- 前景小候选优先于包含它的大区域。
- 每个源像素只分配给一个图层。
- 未被有效候选领取的像素进入 base layer。
- 图层使用源图原始像素，不做羽化或生成式补全。

所有图层重新叠放时应恢复源图。隐藏或移动某层时，底下可能出现透明洞；这正是第一阶段用于检查分层质量的行为，不伪装成已经完成背景修补。

### 5. HTML 渲染器

`machine.html` 使用固定 `863×1823 / DPR 1` 舞台，按原坐标叠放裁切后的透明图层。它提供：

- 图层显示/隐藏。
- 单层棋盘格预览。
- bbox 和 OCR 框开关。
- 临时位移，帮助观察是否存在重影或粘连。
- 图层顺序查看，不将临时调整写回正式数据。
- OCR DOM 草稿开关；默认仍显示源像素文字层，避免机器稿把 OCR 误差伪装成最终结果。

### 6. 综合评审页

`review.html` 集中展示：

- 原图。
- 机器 HTML 捕获图。
- 图层总览与单层预览。
- OCR 文字、置信度和四边形。
- unresolved 候选。
- 冷启动、模型加载、OCR、分割、导出和浏览器捕获耗时。
- 像素覆盖与重新合成差异。

重新合成接近原图是分层算法的机械结果，不作为最终原型质量证明。第一阶段人工验收重点是图层纯度、OCR 正确性和后续可替换性。

## 数据契约

### `ocr.json`

包含 schema 版本、源图 hash、OCR 运行时、模型、耗时和区域数组。每个区域至少包含稳定 ID、四点坐标、bbox、文字、置信度和阅读顺序。

### `layers.json`

每层至少包含：

- 稳定 ID。
- 候选来源：`ocr`、`sam`、`connected-component`、`color-region` 或 `base`。
- bbox、mask、crop、像素数量和 z-index。
- 分割分数、父子关系和冲突处理结果。
- 状态：`accepted` 或 `unresolved`。

### `machine-scene.json`

只引用已导出的本地相对路径，记录 viewport、图层顺序、OCR 草稿和交互元数据。HTML 从 scene 渲染，避免 Agent 手写几百行绝对定位节点。

### `metrics.json`

记录环境、冷/热缓存状态、各阶段耗时、OCR 数量、图层数量、unresolved 数量、像素覆盖率、重新合成差异、资源检查和浏览器检查结果。

### `ai-patch.json`

第二阶段才允许生成。patch 使用受限操作描述：合并、拆分请求、重命名、分组、角色、表示方式、文字修正、bbox、z-index 和样式提示。AI 不直接覆盖原始 OCR 或图层 JSON，也不直接自由重写整份 HTML。

## 两个确认停点

### 停点一：机器 HTML

完成基础加载检查后立即交付 `machine.html` 和 `review.html`。此时只允许说明已运行的机械检查和已知 unresolved 项，不允许继续做 AI 语义调整。等待用户明确指令。

### 停点二：AI 评审 HTML

用户明确要求进入 AI 评审后，生成并应用 `ai-patch.json`，输出第二版 HTML 和前后对比页。再次交付并停止。此时仍不修改正式技能或 React。

## 错误处理

- OCR 或 SAM 核心运行失败：不静默降级，不交付伪正常 HTML；保留诊断，修复后重跑。
- 单个候选失败：标为 `unresolved`，像素保留在 base layer，其他候选继续。
- 模型首次下载：单独记录冷启动耗时；模型缓存命中时记录热运行耗时。
- 源图 hash、模型或参数变化：生成新的缓存键，不复用旧图层。
- 资源或 HTML 加载失败：停在第一阶段内部修复；该修复只处理机械加载问题，不进入 AI 视觉评审。
- 浏览器捕获尺寸不等于 `863×1823 / DPR 1`：视为失败并修复后再交付。

## 验证

### 单元检查

- bbox 与四点坐标归一化。
- IoU、包含关系和候选去重。
- 像素互斥归属和 base layer 回收。
- 稳定 ID 与缓存键。
- scene 相对路径和 schema 校验。

### 单图集成检查

- 输入固定为 `src/resources/image-2.png`。
- 输出 viewport 固定为 `863×1823 / DPR 1`。
- 所有源像素必须被某个图层或 base layer 覆盖。
- 图层重组不得出现未解释的像素缺失或重复归属。
- OCR 四边形、bbox 和图层 bbox 必须在源图边界内。
- 所有 scene 引用的资源必须存在。

### 浏览器冒烟检查

- `machine.html` 与 `review.html` 可打开。
- 无控制台错误和资源 404。
- 显示/隐藏、bbox/OCR 开关、单层预览和临时位移可用。
- 捕获图尺寸正确且非空。

### 第一阶段人工验收

- 文字识别是否足以支持后续 DOM 转换。
- 常见图标、照片、Logo、卡片或装饰是否能成为有意义的独立层。
- 是否存在不可接受的碎片化或错误粘连。
- unresolved 比例是否仍允许 AI 在下一阶段高效修正。
- 机器产物是否比当前 Agent 从零整理素材和 bbox 更适合作为后续输入。

## 第一阶段完成标准

满足以下条件才交付用户：

1. 临时脚本与产物只位于 `.local/`。
2. OCR、SAM 和图层导出均成功。
3. 机械数据、资源、画布和浏览器冒烟检查通过。
4. `machine.html` 与 `review.html` 已生成。
5. 已记录真实耗时和 unresolved 项。
6. 未执行 AI 语义评审、未修改正式技能、未创建 React。

达到上述条件后立即停在用户确认，不自动执行第二阶段。

## 后续正式集成边界

只有机器 HTML 和 AI 评审 HTML 都经用户认可后，才另行设计正式集成：将稳定脚本迁入 `screenshot-to-prototype`，补充正式测试和跨平台安装说明，并把机器底稿与 AI patch 接入现有 reconstruction manifest。现有“HTML 主规格确认后才能转换 React”的规则保持不变。
