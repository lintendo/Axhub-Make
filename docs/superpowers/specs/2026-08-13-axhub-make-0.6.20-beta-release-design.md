# Axhub Make 0.6.20 Beta Release Design

## Goal

Prepare a complete, reproducible Axhub Make beta release without losing work that is still distributed across active branches, worktrees, and uncommitted changes.

The release train produces three independently reviewable deliverables in this order:

1. `@axhub/acp@0.1.13` on npm `latest`;
2. Axhub Make Client Template `0.1.19` on the GitHub primary source and Gitee mirror;
3. `@axhub/make@0.6.20-beta.0` on npm `beta`, plus its matching GitHub prerelease assets.

Codex prepares, builds, verifies, and hashes all artifacts. The human maintainer performs every command that changes npm, GitHub Release, Gitee, or protected remote branch state.

## Release Principles

### Preserve all work before selecting release scope

The current Make development checkout is not a release source. It contains a long-lived branch, active work from multiple tasks, extensive tracked changes, deleted files, and untracked files. Other worktrees and branches are also still active.

The release process must therefore:

- create a new release candidate from the current `origin/main`;
- leave every existing checkout, branch, worktree, index, and untracked file untouched;
- inventory all local and remote branches, worktrees, commits, tracked changes, and untracked files before choosing content;
- assign every discovered feature or fix one disposition: `included`, `deferred`, `duplicate`, `generated`, `local-only`, or `needs-owner-decision`;
- record the exact commit or patch source for every included item;
- require a human decision for unresolved scope instead of silently omitting or including it.

"Complete" means every discovered work item has an explicit disposition and every included item has traceable source evidence. It does not mean merging all dirty files into the release.

### Build from one clean, permanent candidate

The release candidate uses a permanent worktree under an ignored workspace directory, not a `/private/tmp` worktree and not the current dirty checkout. Its branch is based on the latest fetched `origin/main` and uses a `codex/` name.

Only reviewed commits or explicitly captured patches enter the candidate. Generated JavaScript, declaration output, local images, runtime metadata, caches, reports, temporary prototypes, and vendored outputs enter only when their owning build or package contract proves they are required.

The candidate must remain clean after every integration batch. A batch is accepted only after focused tests and independent review. This keeps failures attributable and allows a feature to be deferred without disturbing unrelated work.

## Release Train

### Gate A: Feature completeness and candidate freeze

Create a release-scope ledger from:

- all Make local branches and remote-tracking branches newer than the `0.6.11` release baseline;
- all Make worktrees, including dirty and prunable records;
- current tracked and untracked changes;
- recent design and implementation plans whose implementation status may differ from their documentation status;
- ACP UI source and release artifacts used by the Make assistant and voice paths.

Group related commits and files by user-facing capability rather than by branch name. For each included capability, record:

- source branch, commit list, or patch manifest;
- affected Make server, admin, client template, vendor, and ACP UI boundaries;
- tests already present and tests still required;
- whether it changes the client template payload;
- whether it depends on the new ACP UI online version;
- reviewer decision and final candidate commit.

The scope freezes only after no ledger entry remains `needs-owner-decision`. New work after the freeze is deferred unless the human maintainer explicitly reopens the scope and the affected verification gates are repeated.

### Gate B: ACP UI 0.1.13 online prerequisite

Make's production bootstrap invokes `npx -y @axhub/acp@latest`. Local development may instead auto-discover the sibling ACP UI directory. A local-only validation can therefore pass while the released Make package still starts an older online ACP UI.

ACP UI `0.1.13` must be built and published as a stable release before the Make beta artifact receives final approval. Publishing ACP UI only under `beta` is insufficient because Make resolves `latest`.

The ACP UI directory currently has no Git metadata. Before building, create an ignored release snapshot manifest containing:

- absolute source directory only in the local manifest, never in a published artifact;
- sorted source file list after applying the package's ignore rules;
- SHA-256 for `package.json`, `package-lock.json`, release scripts, voice source, and produced tarball;
- dependency versions relevant to assistant-ui, AI SDK, ACP SDK, LiveKit, React, and Next.js;
- build timestamp and Node/npm versions;
- the release version `0.1.13`.

The ACP UI prepublication gate requires:

- lint and production build;
- ACP core, conversation, Codex P0, provider, attachment, voice-agent, and LiveKit voice regression suites applicable to the accumulated changes;
- public API build and package contract verification;
- npm and pnpm installed-tarball smoke tests produced by the release script;
- tarball content review for secrets, local paths, test data, source-only directories, sourcemaps, and platform-specific native packages;
- human review of the version diff, package contents, release notes, checksums, and exact stable publish command.

After the human publishes `0.1.13`, verification must prove:

- npm `latest` equals `0.1.13`;
- a clean temporary directory installs and starts `@axhub/acp@latest` without access to the local ACP UI source;
- `/`, `/api/chat`, CORS preflight, public API exports, image tooling, and the voice worker are present and operational;
- the running health/version evidence identifies the published package rather than the local checkout.

Failure leaves the Make release blocked. The release process must not change Make to a local path, tarball, or prerelease ACP dependency as a workaround.

### Gate C: Client Template 0.1.19 human review

The client template is an independent deliverable, not an implicit side effect of publishing `@axhub/make`. Its version is `0.1.19` and its release notes must describe only the files and behavior actually entering the template ZIP.

Preparation produces:

- `axhub-make-client-template.zip`;
- `axhub-make-client-template.latest.json`;
- SHA-256 values and archive size/count summary;
- a diff against the published `0.1.18` template at path and content-summary level;
- included, removed, renamed, and excluded file lists;
- dependency and lockfile changes;
- release notes;
- primary GitHub and Gitee publication commands.

The template gate verifies:

- client unit tests, typecheck, and production build;
- release-helper and Gitee mirror tests;
- archive path safety, local-path/secret scanning, exact dependency versions, executable scripts, and absence of local runtime metadata;
- the intended no-local-theme boundary and online primary/fallback design source behavior;
- a clean extracted template can install, build, start, create/open representative resources, and consume the published ACP UI integration where applicable;
- macOS behavior locally and a recorded Windows verification result for command paths and generated client startup.

Codex stops after preparing the review packet. The human maintainer must explicitly approve its contents before running the GitHub and Gitee release commands. After publication, both source URLs, the latest manifest, archive hash, and fallback behavior are verified before Make packaging continues.

### Gate D: Make 0.6.20-beta.0 candidate

The first Make prerelease is `0.6.20-beta.0`, published to npm `beta`. npm `latest` must remain `0.6.11` until a later stable `0.6.20` release is separately approved.

The Make candidate must pin its runtime defaults to Client Template `0.1.19` while continuing to resolve ACP UI through the online `@axhub/acp@latest` production path. The validation environment must disable or remove local ACP UI auto-discovery so it cannot mask registry behavior.

Verification includes:

- repository governance and open-source audit checks;
- release-helper, server, admin, client, vendor, and affected integration tests;
- server and client typechecks;
- admin, client, and complete workspace builds;
- production HTML bootstrap/spec checks where they are existing command-line regression tests, without adding browser HTML validation;
- Make smoke tests and the release script's installed-tarball health probes;
- npm package content, size, executable bit, local path, secret, and self-containment checks;
- a clean temporary install using the produced Make tarball;
- production-mode assistant startup that downloads `@axhub/acp@latest` from the registry;
- assistant chat, image generation, voice entry, voice worker, CORS, project-scoped context, and representative client-template workflows;
- macOS validation and recorded Windows validation for CLI aliases, path quoting, process launch, and installed package startup.

Preparation produces the npm tarball, platform release assets, manifest, SHA-256 file, release notes, verification summary, and exact publication commands. Codex does not execute those commands.

After the human publishes, postpublication checks must prove:

- npm `beta` equals `0.6.20-beta.0`;
- npm `latest` remains `0.6.11`;
- GitHub marks the matching release as a prerelease;
- `npx -y @axhub/make@beta` works in a clean directory;
- the installed package downloads ACP UI `0.1.13` from npm `latest` and discovers Client Template `0.1.19` from the online release sources;
- primary and fallback template delivery both match the approved hash.

## Human Approval Boundaries

Four explicit human decisions are required:

1. approve the completed feature-scope ledger and candidate freeze;
2. approve ACP UI `0.1.13` artifacts and execute its stable npm publish command;
3. approve Client Template `0.1.19` artifacts and execute GitHub/Gitee publication commands;
4. approve Make `0.6.20-beta.0` artifacts and execute npm/GitHub publication commands.

No authorization is implied between gates. Passing a build does not authorize publication, and publishing one deliverable does not authorize the next.

## Failure And Recovery

- A failed integration batch is removed from the candidate by reverting that candidate-only commit, never by rewriting or cleaning the source worktree.
- A failed artifact is rebuilt with an incremented prerelease version if it has already reached npm; published npm versions are never reused.
- If ACP UI stable verification fails after publication, Make remains blocked until a new ACP patch release becomes `latest` and passes the same clean-environment checks.
- If one template source is wrong, do not publish Make against a partially repaired manifest. Repair both the immutable versioned release and latest/fallback routing, then repeat Gate C.
- If postpublication Make beta checks fail, leave `latest` unchanged, document the failure, and prepare `0.6.20-beta.1` from a reviewed fix.

## Evidence And Retention

All generated evidence lives under ignored `.local/release/0.6.20/` directories in the appropriate repository. The final handoff identifies:

- source commit IDs and clean status;
- artifact paths, sizes, entry counts, and SHA-256 values;
- exact commands and exit results;
- skipped environment-dependent checks and their owner;
- human approvals and externally executed commands;
- registry and release URLs returned after publication.

No environment files, access tokens, local absolute paths, authentication output, or raw user data enter a committed or published artifact.

## Non-Goals

- Do not publish stable `@axhub/make@0.6.20` in this release train.
- Do not switch Make production startup to an ACP beta tag or local ACP path.
- Do not merge every branch or dirty file merely because it exists.
- Do not clean, reset, rebase, delete, or repurpose active user worktrees.
- Do not introduce legacy compatibility code to make incomplete candidate content appear compatible.
- Do not let Codex execute commands that mutate npm, GitHub Releases, Gitee Releases, or the protected remote `main` branch.
