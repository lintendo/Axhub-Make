# Voice Commentary Interaction Adapter Design

## Goal

Treat voice as an input/output mode for the existing Make Commentary system. A
spoken action and the corresponding manual action must use the same comment
document, creation operation, direct-run execution, status projection, and
deletion behavior.

## Product Boundary

The voice stack may own audio transport, speech recognition, conversational
history, tool selection, and speech synthesis. It must not own a second comment
store, execution path, task registry, or status lifecycle.

```text
speech
  -> transcript
  -> voice model selects a host tool
  -> thin Make tool adapter
  -> existing Commentary create/query/execute/delete operation
  -> tool result
  -> spoken response
```

Manual Commentary does not depend on the voice tool adapter. Voice depends on
manual Commentary operations, never the reverse.

## Required Behavior

1. Manual `send-to-agent` actions continue to call the established
   `runAnnotationAcpChatPrompt` path directly.
2. Voice comment creation uses Commentary's existing `createVoiceComment`
   entry, which is the programmatic form of the same saved-comment action.
3. Voice execution resolves the existing saved comment and delegates to the
   established direct-run entry. Voice-specific code does not replace manual
   toolbar execution.
4. `axhub_make_list_comments` returns every live comment in the current
   resource document. It exhausts storage pagination internally and does not
   filter by voice source or by a newly derived `pageScope`.
5. Mutations still require real IDs returned by creation/query tools. No IDs
   are inferred from speech or generated by the model.
6. A tool-oriented voice model may take several discovery/tool steps before a
   spoken reply. Exhausting the orchestration budget must produce a truthful,
   user-facing response in the voice layer, never the internal message
   `API 大脑没有返回可播报内容。`.
7. ACP Home voice behavior and Make's existing public voice surface remain
   compatible. The change does not move Make business logic into ACP UI.

## Data and Compatibility

Existing comment documents are authoritative. Older `pageScope` formats and
comments without voice metadata remain queryable. Execution may still validate
that an explicitly selected comment belongs to the visible page; the all-comment
query itself must not discard comments based on page-scope format.

The current voice persistence adapter may project tool execution metadata for
idempotency, but manual UI paths must not call through that adapter. No migration
or rewrite of existing comment documents is allowed.

## Error Handling

- Tool errors stay structured and recoverable at the host-tool boundary.
- The model receives tool results and is allowed enough tool rounds to locate,
  create, and execute a target.
- If no final reply is produced after the bounded rounds, the voice layer says
  it could not finish the operation and asks the user to retry or specify the
  target. It does not claim success and does not expose internal provider names.

## Verification

- A Make regression test proves a manual `send-to-agent` action bypasses the
  voice adapter and reaches the established direct-run function.
- A Make behavior test proves comments with different legacy/current
  `pageScope` values are all returned by the full-list operation.
- ACP voice-client tests prove multi-step tool discovery can exceed four calls
  and that an exhausted tool loop returns a safe spoken response rather than an
  internal error.
- Focused Make tests, ACP voice tests, Make typecheck/build checks required by
  the affected files, and a consumer restart validate the running integration.
