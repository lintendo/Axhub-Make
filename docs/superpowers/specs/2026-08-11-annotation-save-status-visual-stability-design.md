# 批注保存状态视觉稳定设计

## 背景

顶部工具栏会显示 `正在保存 · N 条`、`已保存 · N 条`、`未保存 · N 条`。当前状态节点是居中按钮组的普通 flex 子项，因此文案长度变化会改变整个工具栏的计算宽度，推动按钮组左右抖动。保存很快时，`正在保存` 还会只出现一个短帧，看起来像异常闪烁。

## 目标

- 保存状态文案变化不得改变按钮组的位置。
- 状态区域从按钮组右侧向右自然增长，不压缩或重排按钮。
- 一旦用户看到了 `正在保存`，它至少连续显示 600ms。
- 最终仍由真实保存结果决定：成功显示 `已保存`，失败显示 `未保存`。
- 无批注时继续隐藏整个状态。

## 方案

### 布局

原型批注和文档批注的按钮组都提供一个 `position: relative` 的稳定锚点。保存状态使用绝对定位放在锚点的 `left: 100%` 之外，并保留现有组间距。状态不再参与按钮组宽度和居中计算；文案或数量变长时，只向右扩展。

状态触发区域保留最小宽度以稳定自身视觉，但不设置最大宽度，不截断数量。灰色二级字体、悬停提示和在“退出”之后的视觉顺序保持不变。

### 状态平滑

新增独立的 `useSmoothedAnnotationSaveStatus` 展示层 Hook：

1. 收到 `saving` 时立即显示，并记录开始时间。
2. 收到 `saved` 或 `unsaved` 时，若 `saving` 已展示满 600ms，立即切换；否则等待剩余时长再切换。
3. 等待期间若再次收到 `saving`，取消旧的完成切换，并从新的保存过程重新计时。
4. 初始状态为 `saved` 或 `unsaved` 时直接显示，不人为延迟。
5. 组件卸载时清理计时器。

该平滑仅影响文案展示，不延迟、不重试、也不修改真实持久化流程。

## 测试

- 使用假时钟验证快速成功和快速失败都会让 `saving` 保持 600ms。
- 验证超过 600ms 的保存可立即切换最终状态。
- 验证新一轮保存会取消上一轮待执行的完成切换。
- 工具栏源码契约验证状态采用绝对定位、按钮组提供相对定位锚点，并覆盖原型批注与文档批注两条渲染路径。
- 运行现有保存状态、工具栏和 Commentary 相关回归测试。

## 非目标

- 不改变保存 API、保存重试策略或批注计数口径。
- 不增加进度条、旋转图标或新的颜色状态。
- 不改动其他工具栏按钮的布局和行为。
