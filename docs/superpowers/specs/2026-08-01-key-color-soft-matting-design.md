# 键色软抠图优化设计

## 目标

在不引入模型、Python、ONNX 或新运行时依赖的前提下，改进 Make client 截图还原技能的键色透明化脚本，解决封闭区域残留键色、硬边和键色彩边问题，同时保持现有 CLI 调用兼容。

## 当前问题

- 脚本只从图像边缘洪泛删除键色，无法进入圆环、气泡等被前景包围的封闭背景区域。
- 命中背景的像素直接从不透明变为全透明，没有连续 alpha，抗锯齿、阴影和柔和边缘会产生硬边。
- 透明边缘仍保留与键色混合后的 RGB，合成到其他背景时会出现洋红、绿色或青色轮廓。
- 当前测试只覆盖纯色背景和矩形前景，没有覆盖封闭孔洞、混合边缘或已有 alpha。

## 方案比较

### 方案 A：全局硬阈值

把边缘洪泛改为全图删除键色。实现最小，能清除封闭孔洞，但仍然只有 0/255 alpha，无法解决锯齿和彩边。

### 方案 B：全局软键色与去色溢（采用）

全图识别确定背景，并在背景阈值与前景阈值之间生成连续 alpha；随后根据已知键色和 alpha 反算、限制前景 RGB，降低键色污染。该方案不需要模型或新增依赖，能够覆盖当前主要失败模式。

### 方案 C：完整闭式 matting

从 trimap 求解全图 alpha 和前景色，上限更高，但需要稀疏矩阵求解、较多实现和性能成本，不适合本次脚本级优化。

## 行为设计

`key-transparent-image.mjs` 保留现有必需参数和输出字段：

- `--input`、`--output`、`--key`、`--tolerance`、`--near-tolerance` 和 `--report` 继续有效。
- `tolerance` 表示确定背景阈值；色差不大于该值的像素变为全透明。
- `near-tolerance` 表示确定前景阈值；两个阈值之间使用 smoothstep 生成连续 alpha。
- 默认 `near-tolerance` 调整为足以覆盖常见抗锯齿混色的范围；显式传值仍优先。
- 色差在整张图上判断，不再要求背景与画布边缘连通，因此封闭孔洞可正确透明。
- 新 alpha 与输入图已有 alpha 相乘，不把原有半透明像素错误提升为更不透明。
- 全透明像素的 RGB 归零；软边像素按已知背景色反算前景色并限制到合法通道范围，避免合成彩边。
- 明确前景像素保持原始 RGB 和 alpha，不进行全图颜色修改。

## 质量报告

保留当前报告字段，并补充：

- 全透明、半透明和不透明像素数量及比例。
- 软化边缘像素和去色溢像素数量。
- 处理后仍不透明的键色与近键色像素数量。
- 是否检测到软边，以及处理模式标识。

本次不修改 `audit-assets.mjs` 的退出规则；报告字段先为后续审计增强提供数据。

## 错误与边界

- `near-tolerance` 必须大于 `tolerance`；无有效软区间时给出明确参数错误。
- 键色与主体颜色冲突时可能损伤主体，这是键色法的固有限制；现有 `probe-key-color.mjs` 和生成提示词继续负责避免冲突。
- 不填充透明孔洞，因为孔洞在图标和 Logo 中通常是有效结构。
- 不模糊整个 alpha 通道，避免细小图形和锐利边缘整体失焦。

## 验证

- 失败测试先证明封闭区域中的键色当前保持不透明。
- 失败测试证明键色与前景的混合像素当前不能得到连续 alpha。
- 测试确认软边 RGB 不再保留明显键色污染。
- 测试确认原有半透明度只会保留或降低。
- 测试确认远离键色的主体像素完全不变。
- 运行截图还原图像脚本测试和技能契约测试。
- 使用现有 `government-app-home/asset-sheet-keyed.png` 输出到临时目录，确认封闭键色残留下降且结果包含半透明边缘，不覆盖现有样本。

- 不改变截图还原技能的素材分流策略。
- 不增加旧版本兼容分支。
